# AGENTS.md

本文件用于约束本仓库中与课程内容相关的智能体行为，重点面向以 ipynb 形式编写的深度学习教程，尤其是计算机视觉课程内容。

## 目标

- 产出适合教学的 Jupyter Notebook 教程，而不是只追求可运行的代码草稿。
- 强调“讲清楚为什么”和“讲清楚张量如何流动”，而不只是给出结论。
- 保持内容适合计算机视觉课程语境，默认读者具备 Python 与基础线性代数背景，但不假设读者已经熟悉具体模型实现。

## 适用范围

- `books/**/*.ipynb`：课程正文、模型讲解、算法推导、可视化说明。
- `experiments/**/*.ipynb`：实验型 notebook，但仍应保持教学可读性。
- `README.md`、章节说明文档：若与 notebook 内容联动，应保持术语一致。
- `book_generate.sh`、`book_start.sh`、`.github/workflows/pages.yml`：课程站点构建、预览与发布脚本，修改前必须先阅读现有内容并保留项目特定配置。

## 总体写作原则

- 默认使用中文写作；首次出现的重要英文术语可在括号中保留英文原文。
- 优先采用“概念说明 -> 数学/直觉 -> 代码实现 -> 结果解释”的组织方式。
- 一节只解决一个清晰问题，避免在单个 notebook 中同时塞入过多主题。
- 示例应尽量小而完整，优先选择能快速运行、方便观察中间结果的配置。
- 若存在工程写法与教学写法冲突，优先选择教学更直观的写法，并在必要时说明工程实现上的等价形式。
- 除非用户明确要求，否则不要为了“现代化”而引入过多与教学主线无关的工程抽象。

## Notebook 原则

每个教学型 ipynb 应尽量包含以下层次：

1. 核心概念或公式：只保留理解实现所必需的推导与定义。
2. 代码实现：按模块拆分，不要把完整实现挤在单个大代码单元中。
3. 最小可运行示例：给出可以直接验证结果的输入、输出或可视化。
4. 接口明确：输入输出关系、适用场景与局限性。
5. 可解释性：优先提供可视化解释，比如GradCAM，Attention Map
6. 张量流动：在文字、表格或代码注释中说明输入、输出和关键中间张量形状。
7. 结果解释：可视化或指标输出之后，必须解释应观察到的现象、正常结果和常见失败模式。

## Notebook默认模板

1. 学习目标：说明本节要解决什么问题、读者将学到什么。
2. 研究背景与直觉：形式化的问题定义、解释问题动机、任务场景、为什么需要该方法。
3. 数据集与任务定义：先说明任务的一般定义、原始数据格式、标签形式、当前选用的特征与任务的数学形式化。
4. 损失函数定义：在任务和标签形式明确后，再说明损失函数的选择、公式和适用条件。
5. 模型框架：解释模型整体如何匹配前面的任务输入、输出、标签和损失目标。
6. 模型组件：说明组件内部构成，比如 Transformer 编码器内部构造：自注意力机制和前馈神经网络。
7. 模型训练过程：学习率，早停机制等。
8. 最小可运行示例与结果解释：在验证级样例上的结果和可视化。
9. 小结
10. 参考资料与延伸阅读：当前论文的相关解读、其他相关论文

新增 notebook 时默认使用以上模板。除非现有章节风格明显不同，notebook 标题使用一级标题，其余主要章节使用二级标题。Markdown 与代码应交替出现，不要把整节实现写成一个长代码块。

## Annotated Book 工作流

创建或大幅修改教学 notebook 时，应按以下顺序工作：

1. 阅读 `AGENTS.md`，并把它作为本仓库课程内容的最高约束。
2. 检查 `books/`、`codes/`、`papers/`、`slides/` 中是否已有相关材料。
3. 优先复用 `codes/` 或邻近 notebook 中已有的模块、训练循环、可视化工具；若为了教学需要重写，应说明与工程实现的关系。
4. 若模型或流程结构明确，加入简洁的 Mermaid 图，展示数据流、模型组件、训练循环或可视化流程。
5. 若主要模块的输入输出形状明确，加入张量流表。推荐列为：`阶段/模块`、`输入形状`、`操作`、`输出形状`、`说明`。
6. 若形状、结构或论文细节不确定，不要编造；应省略对应表格/图示，或明确标注不确定性。
7. 增加最小可运行示例或可视化，并在图前说明“要看什么”，图后说明“看到了什么”。
8. 若项目使用显式 `_toc.yml` 或手动目录索引，应同步更新导航；若由 `book_generate.sh` 自动生成目录，则无需手动改 TOC。

维护课程站点时遵循以下约定：

- 构建书籍优先使用 `./book_generate.sh`；常用形式为 `./book_generate.sh ./books ./_build/books directory`。
- 本地预览优先使用 `./book_start.sh`；若默认端口被占用，可通过 `PORT=...` 指定端口。
- 修复 GitHub Pages 发布时，先阅读 `.github/workflows/pages.yml`；保留已有分支、Python 版本、安装步骤和构建参数等项目特定配置。
- 不要提交、推送或部署，除非用户明确要求。

## Markdown 单元规范

- 标题要直接表达教学意图，例如“卷积为什么能提取局部特征”“多头注意力的张量形状变化”。
- 段落应短，避免大段堆砌；优先使用短句和分点说明。
- 数学公式只保留必要部分，重点解释符号含义与张量维度。
- 讨论模型时，必须明确输入形状、输出形状，以及关键中间张量的形状变化。
- 若模型或流程适合图示，应优先使用 Mermaid 或已有图片说明结构；Mermaid 节点命名应短、清晰，并与正文术语一致。
- Mermaid 图中若同时包含张量和模块，应尽量用不同形状或颜色区分：张量/变量统一使用白底圆角节点，模块/操作使用矩形、菱形或其他颜色。
- Mermaid 中张量/变量节点推荐写法为 `X(["变量名<br/>(B, C, H, W)"])`，并配合 `classDef tensor fill:#ffffff,stroke:#2563eb,color:#0f172a,stroke-width:1.5px;`。
- 张量流表只写有根据的形状；不要为了表格完整而虚构维度。
- 可视化前先说明“要看什么”，可视化后再解释“看到了什么”。
- 对比不同方法时，先给比较维度，再给结论，不要直接下判断。
- 思考题以markdown detail的形式折叠答案

## 代码规范
- 优先复制codes下的代码实现，保持不同notebook间，同样的模块实现尽量一致：比如统一MultiHeadAttention
- 代码简洁易读，教学演示用：比如不要为了可扩展性，保留太多根本用不到的参数
- 与pytorch官方实现尽量靠近：可以在官方基础上进行简化
- 新增模型代码前，先检查 `codes/` 和邻近 notebook；只有在教学清晰度需要时才展开实现。
- 对共享模块、训练循环、指标函数和可视化函数，优先保持同一课程内接口一致。
  

## 数据处理
- 数据集预处理逻辑在prepare_data.md中进行说明，原始数据集如何预处理和划分可以在prepare_data.sh或prepare_data.py中实现。
- 大多数情况下，notebook中重点放在模型和训练过程，可直接调用已经预处理完成的数据。

## 参考资料
- slides目录中的对应教学内容优先参考，同时参考优质课程如cs231n
- papers目录中的对应论文优先参考

## 计算机视觉内容约束

- 默认围绕图像分类、目标检测、语义分割、特征提取、视觉 Transformer、卷积网络等常见课程主题展开。
- 介绍视觉任务时，要明确数据表示方式，例如 RGB 图像张量通常写为 `(B, C, H, W)`。
- 介绍 CNN 时，要明确卷积核、步幅、填充、感受野及特征图尺寸变化。
- 介绍 Transformer 或视觉注意力模型时，要明确 patch、token、embedding、位置编码与注意力矩阵的形状。
- 若引入数据增强、归一化、损失函数、评价指标，需说明它们在视觉任务中的作用，而不是只给 API。

## 教学风格偏好

- 优先使用“先直觉、后公式、再代码”的顺序。
- 优先展示小样本、小模型或小尺寸输入，便于读者观察结果。
- 优先解释失败案例、边界条件和常见误区。
- 如果一个抽象会明显降低初学者可读性，优先展开写法。
- 不要使用空泛表述，如“这里很容易理解”“读者可以自行验证”。应明确指出应观察的现象。

## 与现有项目风格保持一致

- 本仓库整体参考 annotated 风格，内容应兼顾讲解与实现。
- 延续 Jupyter Book 友好的组织方式，保证 Markdown 与代码交替自然。
- 若修改已有 notebook，应优先保持原有章节节奏、术语与叙述风格一致。
- 若发现内容相对参考资料做了教学性精简，不应自动补回，除非用户明确要求扩展。

## 输出质量要求

- 新增或修改 notebook 内容后，应至少进行一次最小验证：运行受影响代码单元，确认没有明显语法或名称错误。
- 若完整运行成本较高，至少验证 notebook JSON、导入、模型前向形状和轻量级样例。
- 若 notebook 中包含训练过程，优先提供轻量验证版本，而不是默认运行长时间训练。
- 若修改影响公式、维度、章节目录或图示说明，应同步检查前后文是否一致。
- 发现参考资料与现有 notebook 不一致时，只将“明确错误”视为必须修正项；若只是教学性删减，应保留。

## 禁止事项

- 不要无说明地引入大段与课程目标无关的工程脚手架。
- 不要把教程写成 API 罗列或论文翻译。
- 不要省略关键张量维度、输入输出关系、掩码含义或训练目标说明。
- 不要为了追求代码复用而牺牲初学者阅读路径。
- 不要默认读者已经理解数据集背景、任务定义或可视化含义。
- 不要无根据地补充论文、模型结构、数据划分或指标结果。

## 推荐的单元自检清单

在编写或修改教学 notebook 时，优先自检以下问题：

- 本单元是否清楚说明了目的？
- 本节是否说明了输入、输出和关键中间张量的维度？
- 代码是否能被读者按顺序直接运行？
- 是否存在不必要的工程抽象影响理解？
- 是否给出了足以支持结论的最小示例或可视化？
- 公式、文字、代码注释和实际实现是否一致？
